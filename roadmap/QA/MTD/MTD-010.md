# MTD-010 — Controle Administrativo de Acesso (Prorrogar/Cortar) + Gate de Plano Ativo

## Flow
[FLOW-013](../Flow/FLOW-013.md) — Controle Administrativo de Acesso + Gate de Plano Ativo

## Objetivo
Verificar ponta a ponta que o admin (Douglas) consegue prorrogar trial ou cortar acesso de um
usuário (dois níveis) pela UI, que o efeito aparece em `/me/access-context`, que o login passa a
respeitar isso — incluindo o caso de "filhos" sem billing próprio — e que o assistente de IA e as
notificações operacionais passam a silenciar fora de `FULL_ACCESS`, sem afetar notificações de
billing nem organizações saudáveis.

## Pré-condições
- Branches `feature/EPIC-041-admin-access-control` (api PR #178, web PR #127) rodando localmente
  (api porta padrão local, web `npm run dev`) ou já mergeadas em `staging`.
- Pelo menos 3 usuários de teste:
  - **Usuário Dono A** — dono de conta com assinatura própria (`BillingSubscriptionItem` tipo
    `USER`), organização própria sem mais ninguém vinculado.
  - **Usuário Dono B** — dono de conta com assinatura própria, organização com pelo menos 1 membro
    de equipe convidado (**Membro B1**) sem billing individual.
  - **Membro B1** — pertence só à organização do Dono B (nenhuma outra organização saudável).
  - Opcional, para o cenário de multi-org: **Membro B2** — pertence à organização do Dono B **e**
    a uma segunda organização saudável e independente.
- Login admin do Douglas em `/private/admin/billing/subscriptions`.
- Acesso ao banco para confirmar `billing_subscription`/`billing_subscription_item` e, se
  aplicável, `assistant_link`/organizações envolvidas.
- Pelo menos uma organização com assistente de IA habilitado (EPIC-031) e com notificações
  WhatsApp configuradas, para o Cenário 7.

## Cenário 1 — Prorrogar trial

### Passos
1. Em `/private/admin/billing/subscriptions`, localizar o item tipo `USER` do Dono A (status
   `TRIAL`).
2. Clicar em "Prorrogar trial", confirmar que o campo de data vem preenchido com +15 dias por
   padrão, ajustar se quiser, confirmar.
3. Logado como Dono A, chamar `GET /me/access-context` (ou abrir a tela que o consome).

### Resultado Esperado
- `currentPeriodEnd` atualizado no banco para a nova data
- Status permanece/retorna para `TRIAL`
- `/me/access-context` do Dono A reflete a nova data imediatamente, sem precisar de novo login

### Evidência
- [ ] Print do modal preenchido e da confirmação
- [ ] Print do banco (`billing_subscription.current_period_end`)
- [ ] Print de `/me/access-context` com a nova data

## Cenário 2 — Cortar acesso: somente leitura

### Passos
1. No mesmo painel, no item do Dono A, clicar "Cortar acesso", selecionar "Somente leitura",
   preencher motivo (ex. "teste MTD-010 — leitura"), confirmar.
2. Logado como Dono A: tentar logar normalmente (deve funcionar) e tentar uma ação de escrita (ex.
   criar um chamado/manutenção).

### Resultado Esperado
- Status vira `CANCELED` no banco, auditoria registrada com motivo
- Dono A consegue logar e navegar em modo leitura
- Qualquer escrita protegida por `@RequiresFullAccess` é bloqueada

### Evidência
- [ ] Print da confirmação do corte
- [ ] Print do login bem-sucedido
- [ ] Print do erro ao tentar escrever

## Cenário 3 — Cortar acesso: bloqueio total

### Passos
1. No item do Dono A, "Cortar acesso" → "Bloquear login", motivo obrigatório preenchido, confirmar.
2. Tentar logar como Dono A (sessão nova, sem token anterior).
3. Se o Dono A tiver uma sessão/token ainda válido de antes do corte, confirmar que ele **continua**
   acessando com esse token (decisão de produto: sem invalidação ativa) — não é bug.

### Resultado Esperado
- Status vira `BLOCKED` no banco
- Nova tentativa de login retorna erro distinto de senha incorreta (ex. "Acesso suspenso. Contate
  o suporte."), não a mensagem genérica de credenciais inválidas
- Sessão/token já emitido antes do corte continua funcionando (comportamento esperado, não bug)

### Evidência
- [ ] Print do corte confirmado
- [ ] Print do erro de login distinto do erro de senha incorreta

## Cenário 5 — Usuário sem nenhuma assinatura → 404

### Passos
1. Identificar (ou criar) um usuário sem nenhum `BillingSubscriptionItem` tipo `USER`.
2. Chamar `POST /private/admin/billing/users/{userId}/subscription/extend-trial` e
   `/restrict-access` para esse usuário.

### Resultado Esperado
- `404 Not Found` nos dois endpoints — nenhuma assinatura é criada do zero (fora de escopo,
  confirmado na spec)

### Evidência

## Cenário 6 — Cascata dono → organização → "filhos"

### Passos
1. Cortar o acesso do Dono B com "Bloquear login" (mesma mecânica do Cenário 3).
2. Confirmar no banco que o `BillingSubscription` do item `ORGANIZATION` da organização do Dono B
   é o mesmo registro do item `USER` dele (já deveria ser, por design existente) e que o status
   mudou para os dois.
3. Tentar logar como **Membro B1** (só pertence à organização do Dono B).
4. Se houver **Membro B2** (também em outra organização saudável), tentar logar como ele.
5. Tentar interagir com o assistente de IA como Membro B1 (ou qualquer usuário da organização do
   Dono B), via WhatsApp ou canal configurado.
6. Disparar uma das 5 notificações operacionais para a organização do Dono B (ex. criar um novo
   chamado de morador, se `ResidentTicketAdminNotificationService`/`WhatsApp` estiver no caminho).

### Resultado Esperado
- Passo 3: Membro B1 **não consegue logar** (mensagem de acesso suspenso, não senha incorreta)
- Passo 4: Membro B2 **continua conseguindo logar** (tem outra organização saudável)
- Passo 5: assistente nega a conversa (não responde, ou responde com mensagem de acesso
  suspenso/indisponível, conforme o tratamento de `AssistantAccessGuard` no canal)
- Passo 6: nenhuma notificação chega (WhatsApp/e-mail) para a organização do Dono B; logs mostram
  o skip, sem exceção/erro no restante do fluxo que disparou a notificação

### Evidência
- [ ] Print do banco confirmando mesmo `BillingSubscription` para item `USER` e `ORGANIZATION`
- [ ] Print da tentativa de login do Membro B1 falhando
- [ ] Print da tentativa de login do Membro B2 funcionando (se aplicável)
- [ ] Print/log do assistente negando a conversa
- [ ] Print/log confirmando que a notificação não foi enviada

## Cenário 8 — 2FA com acesso bloqueado

### Passos

2. Tentar logar: inserir e-mail/senha corretos, chegar até a etapa de 2FA, inserir o código

### Resultado Esperado
- Mesmo com e-mail/senha e código 2FA corretos, o login é negado na etapa de `verifyTwoFactor()`

## Notas / Riscos
- Cenário 3 (sessão/token já emitido continuar funcionando após o corte) **não é bug** — é decisão
  de produto confirmada pelo Douglas (sem invalidação ativa de sessão nesta entrega). Não reportar
  como falha.
- Este fluxo toca `UsersService.authenticate()`, usado por **todo** login do sistema — qualquer
  anomalia fora dos usuários de teste (ex. um cliente real não conseguindo logar sem ter sido
  tocado por este fluxo) é crítico e deve interromper a homologação imediatamente.
- Testar o Cenário 6 numa organização de teste isolada, nunca na organização real de produção do
  Douglas, para não cortar acidentalmente o próprio acesso dele em produção.

## Resultado da Execução (04/11/2026)

Executado localmente (api porta 9000 perfil `local` + web `npm run dev`), com usuários sintéticos
criados via `/dev/simulate/affiliate-flow` (dev-only) + convite real de equipe — nenhum usuário real
(incluindo a conta do próprio Douglas, id=1) foi tocado por nenhuma chamada deste QA.

- [x] **Cenário 1** — Prorrogar trial: `POST extend-trial` força `TRIAL` e atualiza
      `currentPeriodEnd`; `/me/access-context` do usuário reflete a nova data imediatamente
      (`trialExpiresAt`), sem precisar de novo login. **Confirmado também pela UI** (botão → modal
      pré-preenchido com +15 dias → banco atualizado).
- [x] **Cenário 2** — Cortar "somente leitura": status vira `CANCELED`; login continua funcionando;
      tentativa de escrita (`POST /organizations`) retorna `403 subscription-denied` com mensagem
      clara.
- [x] **Cenário 3** — Cortar "bloqueio total": status vira `BLOCKED`; login seguinte retorna
      `403 forbidden` ("Acesso suspenso. Contate o suporte."), distinto do `401` genérico de senha
      incorreta (testado lado a lado).
- [x] **Cenário 4** — Motivo obrigatório: back rejeita com `422` (`reason` vazio ou ausente); front
      bloqueia o submit com toast "Informe o motivo do corte de acesso", sem disparar request —
      confirmado via rede (nenhuma chamada ao back até preencher o motivo).
- [x] **Cenário 5** — Usuário sem assinatura: `extend-trial` e `restrict-access` retornam `404`
      ("Assinatura não encontrada para o usuário") sem criar nada.
- [x] **Cenário 6** — Cascata dono→organização→"filhos": confirmado no banco que item `USER` e
      `ORGANIZATION` do dono compartilham a mesma `BillingSubscription`; ao bloquear o dono, (a) o
      próprio dono não loga mais, (b) um "filho" vinculado só àquela organização também não loga
      mais (fix do TASK-397 funcionando — sem isso ele ficaria órfão), (c) um segundo "filho" ligado
      também a uma organização saudável **continua logando normalmente**. Não cobri aqui o efeito no
      assistente de IA / 5 notificações — exigiria configurar WhatsApp/assistente localmente
      (tokens dummy); essa parte permanece coberta só pelos testes automatizados dedicados por
      serviço (ver TASK-399), que passam 100%.
- [x] **Cenário 7** — Organização saudável: login e escrita (`POST /organizations`) funcionam
      normalmente para um dono não tocado pelos cortes acima — sem regressão.
- [ ] **Cenário 8** — 2FA: não executado ao vivo (exigiria montar um fluxo TOTP completo); a mesma
      lógica (`resolveLoginAccessMode` em `verifyTwoFactor()`) está coberta por
      `UsersServiceTwoFactorAccessTest` (TASK-QA-AUTO-010), que passa 100%. Recomendo validação
      manual pontual por quem tiver 2FA configurado antes do merge, mas não é bloqueador dado o
      teste automatizado dedicado.

### Bug encontrado e corrigido durante a execução
Ao testar o Cenário 1 pela UI, os botões **"Prorrogar trial"/"Cortar acesso"** desapareceram da
linha assim que o status deixou de ser `ACTIVE` (virou `TRIAL`) — e, ao investigar, qualquer usuário
já em `TRIAL`/`CANCELED`/`BLOCKED` nunca via esses botões, porque `actionBtns()` só renderizava
botões quando `status === "ACTIVE"`. Isso escondia justamente os dois casos de uso centrais do
épico: agir sobre um usuário **em trial** (o motivador inteiro da feature) ou reverter um corte já
feito. Corrigido em `easy-maintenance-web` commit `c99d18e` (mesma branch do épico): Upgrade/
Downgrade/Cancelar continuam restritos a `ACTIVE`, mas Prorrogar trial/Cortar acesso agora aparecem
para qualquer status, alinhado com o backend (que nunca teve essa restrição). Revalidado via UI:
botões aparecem para `TRIAL`/`BLOCKED`, fluxo completo (clique → POST → banco) confirmado para os
dois endpoints. `tsc --noEmit` e `npm run build` limpos após o fix.

### Achado secundário (não corrigido, fora de escopo do épico)
A tabela de `/private/admin/billing/subscriptions` não atualiza visualmente após aplicar um filtro
("Responsável") nem sempre reflete imediatamente o resultado de uma mutação (ex. após Prorrogar
trial, a linha às vezes continua mostrando o status antigo até navegar away e voltar) — confirmado
via rede que a API responde corretamente (200, dados corretos) em ambos os casos; o problema é de
re-render no componente, pré-existente à esta entrega (a tela e o filtro já existiam antes do
EPIC-041). Não bloqueia a feature (os dados reais estão sempre corretos no banco/API), mas atrapalha
a experiência do Douglas ao usar os novos botões — vale uma task de UI separada se ele achar
incômodo no uso real.
